# مبلغ سفارش (`total_price`) — وضعیت فعلی فرانت

قرارداد بک‌اند: `FRONTEND_SERVICE_RATES.md` (ریشه‌ی مخزن).

نکته‌ای که همه‌ی این سند از آن می‌آید: **بک‌اند `total_price` را بازمحاسبه
نمی‌کند.** هر عددی که بفرستیم مستقیم در `orders.pakar_price` می‌نشیند (§۶ سند).
پس اشتباهِ فرانت = مبلغِ غلطِ سفارشِ واقعی.

## نرخ از کجا می‌آید

```
POST /api/steps/fetch { categoryId }
  → steps[group][field].field_details[i].price     ← نرخ هر گزینه
                                        .value     ← انتخاب کاربر (فرانت پر می‌کند)
```

مبلغ پایه = مجموع `price × value` روی گزینه‌های انتخاب‌شده. همین `steps` پرشده
هم باید در بدنه‌ی `/orders/submit` برود، چون بک‌اند `order_details` را از آن
می‌سازد (§۵).

## یک هسته‌ی محاسبه، دو مسیر ثبت

جمع مبلغ فقط در `services/orderPricing.js` انجام می‌شود:

| تابع | کار |
| --- | --- |
| `calculateStepsPrice(steps)` | `{ total, showPrice }` از روی ساختار `steps` |
| `applySelectionsToSteps(apiSteps, lines)` | نشاندن انتخاب‌های فرمِ محلی روی مراحل API |
| `priceSelections(apiSteps, lines)` | هر دوی بالا با هم |

### مسیر ۱ — سفارش عادی مشتری

`screens/category/Preview.js` ← `selectTotalPrice` در `slices/stepSlice.js`
(که همان `calculateStepsPrice` است). کاربر مستقیم روی ساختار API انتخاب می‌کند،
پس نگاشتی لازم نیست.

قواعدی که این محاسبه رعایت می‌کند (همه تست دارند —
`slices/__tests__/stepSliceTotalPrice.test.js`):

- فقط گزینه‌ی انتخاب‌شده شمرده می‌شود؛ مقدارِ رشته‌ای `"0"` یعنی انتخاب‌نشده.
- ضرب در تعداد فقط برای شمارنده‌ها (`has_counter` / `type: counter`). مقدارِ
  فیلد `input` متنِ کاربر است، نه تعداد.
- `affect_on_price === 0` از جمع بیرون می‌ماند. **نبودِ** این فیلد در پاسخ به
  معنی صفر نیست.
- `price: null` یعنی «نرخ تعیین‌نشده»، نه رایگان → `showPrice = false` و UI
  به‌جای عدد «نیاز به بررسی» نشان می‌دهد.
- خروجی همیشه عددِ صحیحِ غیرمنفی است (§۴ سند).

### مسیر ۲ — سفارش‌های سازمانی

`screens/orders/OrderSummaryScreen.js` ← `hooks/useCategoryRates.js`.

این مسیر (کاشی‌های «انتخاب سیستماتیک» و «انتخاب جامع») فرمش محلی است
(`org/systematicFlows.js`) و شناسه‌ی فیلدهای بک‌اند را ندارد. هوک، مراحلِ همان
`category_id` را از `/steps/fetch` می‌گیرد و انتخاب‌های کاربر را **بر اساس
برابریِ عنوانِ نرمال‌شده** رویش می‌نشاند:

- `{ label: 'نصب سیستم عامل', value: 'ویندوز 11' }` → گزینه‌ی «ویندوز 11»، مقدار ۱
- `{ label: 'لپ تاپ', value: 3 }` → گزینه‌ی «لپ تاپ»، مقدار ۳
- `{ label: 'لپ تاپ / آکبند', value: 2 }` → گزینه‌ی «آکبند» زیر فیلدِ «لپ تاپ»

نرمال‌سازی فاصله/نیم‌فاصله، ی و ک عربی و ارقام فارسی را یکدست می‌کند، پس
«لپ تاپ»، «لپ‌تاپ» و «لپتاپ» یک کلید می‌دهند.

**قواعد محافظه‌کارانه‌ی نگاشت** (تست: `services/__tests__/orderPricing.test.js`):

- عنوانی که به بیش از یک گزینه بخورد **حدس زده نمی‌شود**؛ رد می‌شود و در
  `ambiguous` گزارش می‌گردد.
- هر گزینه فقط یک‌بار شمرده می‌شود.
- عنوان‌هایی که معادلی ندارند در `unmatched` جمع و یک‌بار با `console.warn`
  چاپ می‌شوند (در بیلد production هم باقی می‌ماند). این لاگ همان جایی است که
  فرمِ محلی و کاتالوگِ بک‌اند از هم دور افتاده‌اند.
- اگر **هیچ** گزینه‌ای نخورد → `total_price: 0` و `steps: []`، یعنی همان سفارشِ
  «استعلامی» قبلی. عددِ ساختگی فرستاده نمی‌شود.

تا رسیدنِ پاسخِ نرخ‌ها، دکمه‌ی «ثبت نهایی» سفارش را رد نمی‌کند (وگرنه سفارش با
مبلغ صفر ثبت می‌شد). مبلغ پیش از ثبت، روی رسید (`withReceiptTotal`) یا در ردیف
«هزینه» نشان داده می‌شود — همان عددی که ارسال خواهد شد.

## کارهای باقی‌مانده

- **نگاشت عنوان‌محور موقتی است.** راه‌حل پایدار این است که فرمِ سازمانی خودش از
  `/steps/fetch` ساخته شود (مثل مسیر عادی) تا شناسه‌ها واقعی باشند. تا آن وقت،
  هر تغییرِ عنوان در پنل بک‌اند می‌تواند بی‌صدا یک قلم را از مبلغ بیندازد —
  فقط `console.warn` بالا از آن خبر می‌دهد.
- **`org/HardwareSelectionScreen.js` و `screens/DeviceModelInfoScreen.js`
  اصلاً `categoryId` پاس نمی‌دهند**، پس ثبتِ سفارششان با «دسته‌بندی سفارش
  نامعتبر است» رد می‌شود — مستقل از قیمت. تا وقتی شناسه‌ی دسته‌ی درستشان
  مشخص نشود، نرخی هم نمی‌توان برایشان گرفت.
- تخفیف/کد معرف و مبلغ نهایی پرداخت از پاسخ endpointهای بعدی می‌آیند، نه از این
  محاسبه (§۷ سند).
